# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

Krevyon's own marketing/showcase site — a static site (no framework, no package.json, no runtime build step) that sells the agency by being a well-executed example of its own work. It ships as two independent, fully static, fully indexable HTML pages — Spanish at `/` and English at `/en/` — generated from one shared template. See `PRODUCT.md` for full product context (audience, positioning, brand commitments, constraints) and `DESIGN.md` for the complete visual design system (palette, type, components, named rules, do's/don'ts). Read both before making non-trivial changes — this repo encodes a lot of prior design decisions and explicitly-rejected alternatives that are easy to accidentally reintroduce.

## Running it

No install and no build step to *view* the site.

- Open `index.html` directly in a browser, or
- Serve it statically: `python -m http.server 8000` then open `http://localhost:8000` (also visit `/en/` for the English page)

There is no test suite or linter. The one generation step that does exist — regenerating `index.html`/`en/index.html` from the template after a content edit — is covered under Architecture below; it needs Node but nothing gets installed (`node scripts/build-pages.mjs`, zero npm dependencies).

## Architecture

**Never hand-edit `index.html` or `en/index.html` directly — both are generated output.** The single source of truth for markup and Spanish copy is `templates/page.template.html`; running `node scripts/build-pages.mjs` reads it plus the dictionary in `i18n/dictionary.mjs` and writes both `index.html` (es, site root) and `en/index.html` (en), rewriting asset paths, injecting per-locale `<title>`/meta/canonical/hreflang/JSON-LD, and swapping the nav language-switch links. If you edit `index.html` by hand, your change is silently overwritten the next time someone runs the generator — edit the template instead, then regenerate. Both output pages share sections in reading order, each `<section id="...">`: `inicio` (hero) → `servicios` → `por-que` → `construimos` (six business-type tabs) → `showcase` (device-mock composition) → `proceso` → `fortalezas` → `experiencia` → `valor` → `faq` → `contacto` — the ids themselves are not translated, so an in-page anchor like `#servicios` is identical and safe to link to on either page.

**Why two real pages instead of a JS language toggle.** An earlier pass swapped all text client-side with JavaScript; a search engine only ever indexes whatever the server actually sends, so that approach meant only one language could ever be indexed. `/` and `/en/` are each complete, crawlable HTML with their own `<title>`, meta description, `rel="canonical"` (self), and `rel="alternate" hreflang`. Never reintroduce a runtime full-page text-swap for content that needs to be indexed in both languages.

**Bilingual content lives in `i18n/dictionary.mjs`, consumed only at generation time.** Every user-visible string (nav, hero, section copy, mock-UI text, FAQ, footer, `<title>`/meta tags) has an entry keyed `{ es, en }`, and the corresponding element in `templates/page.template.html` carries `data-i18n="that.key"` — Spanish text as the element's actual content (so the template itself is a readable, reviewable Spanish page). When the text to swap is an attribute rather than the element's content (an `aria-label`, a `<meta content>`), add `data-i18n-attr="attribute-name"` alongside it. `scripts/build-pages.mjs` strips both authoring attributes from the shipped output — they're a build-time marker, not runtime API. Adding a new translatable string means adding one dictionary entry with both languages, then rerunning the generator — never a hardcoded second-language string anywhere else, and never a client-side dictionary shipped to the browser again (that used to be `js/i18n.js`, ~31KB of JS executing ~230 DOM mutations on every load; it no longer exists). If an element mixes an icon/SVG with translatable text (e.g. a FAQ question, a strengths-list check item), wrap only the text in its own `<span data-i18n="...">` in the template — setting the whole element's content would wipe the icon.

**Config-driven content, not hardcoded markup.** All contact links and reused brand copy (WhatsApp/Instagram/email links, tagline, primary CTA label) live in `js/config.js` as `window.KREVYON_CONFIG` (browser-side; used identically by both generated pages). `js/main.js` wires this up at load: elements tagged `data-link="whatsapp|instagram|email"` get their `href` set from config, and elements tagged `data-config="<key>"` get their `textContent` set from config. `i18n/site.mjs` holds the small overlapping set of build-time-only constants (production domain, email, Instagram — used for canonical/hreflang/JSON-LD by `scripts/build-pages.mjs`, which runs in Node and can't reach into `window.KREVYON_CONFIG`); keep the two in sync by hand if contact details change. Never hardcode a contact link or reused brand string directly in the template — add/edit it in `config.js` and reference it via `data-link`/`data-config`.

**Two-tier motion system, deliberately layered and deliberately load-ordered:**
- `js/main.js` — the baseline: nav scroll state, mobile menu, `IntersectionObserver`-driven scroll reveals (`data-reveal`), the build-section tablist (`data-build`, full roving-tabindex keyboard support, crossfade between panels), the FAQ accordion, and cursor-tracked spotlight/parallax effects. Loaded with `defer`, runs immediately — nothing in this file waits on a third-party network request.
- `js/motion-loader.js` — loaded with `defer` right after `main.js`; does nothing until the page's `load` event fires and the main thread is idle (`requestIdleCallback`, with a `setTimeout` fallback), and does nothing at all if `prefers-reduced-motion` is set. Only then does it inject GSAP + ScrollTrigger from CDN and, once those resolve, `js/motion.js`.
- `js/motion.js` — pure progressive enhancement (hero ring/mark scroll drift, staggered showcase panel entrances, KPI count-up, process-line fill) — unchanged in behavior from before, just loaded later and lazily by `motion-loader.js` instead of as a blocking `<script>` in the critical path. It still no-ops immediately if `window.gsap`/`window.ScrollTrigger` are somehow missing. **The site must be fully usable, visible, and animated via CSS + `main.js` alone** — never make `motion.js`/GSAP required for content to appear, and never move GSAP back to a blocking script tag ahead of `main.js`: nothing it animates lives in the first viewport, so it has no business competing with `main.js`/the hero for bandwidth or CPU during page startup. A synchronous inline `<script>` at the top of `<body>` adds a `.js` class specifically so JS-gated starting-hidden states (reveals, GSAP opacity) default to visible if JS fails.

**Hero 3D scene (`js/hero-scene.js`) is also lazy and tiered by device.** Loaded as a native ES module (already deferred by the HTML spec), it imports the minified Three.js build (`three.module.min.js`, roughly half the bytes of the default `three.module.js` for an identical API — always use the `.min` build here) and defers its own heavy scene construction (~80 meshes) to `requestIdleCallback` so it doesn't compete with the rest of page startup. It disables antialiasing and halves its effective frame rate on coarse-pointer (touch) devices — a far more reliable weak-GPU signal than viewport width — respects `prefers-reduced-motion` (renders one static frame, no render loop at all), and pauses its render loop via `IntersectionObserver` whenever the hero scrolls out of view. Keep all four of these when touching this file; none of them are optional hardening, they're why a decorative background scene doesn't cost battery/CPU once the visitor has scrolled past it or is on a phone.

**Images ship as `<picture>` with a WebP source and a real, correctly-sized JPEG fallback — never a raw multi-megabyte upload.** Every photo under `uploads/` (and the nav/footer logo icon under `assets/`) is pre-resized to roughly 2–3× its largest actual on-page display size and re-encoded before it ever gets referenced from the template; there is no image-processing step at build time, the checked-in files are already the optimized ones. If you add a new real photo, resize and dual-encode it the same way (Pillow: resize to the container's rendered size × ~2.5, save both `.jpg` — `quality≈80, optimize=True, progressive=True` — and `.webp` — `quality≈80, method=6`) before wiring it into the template with `<picture><source type="image/webp">…<img width height loading="lazy" onerror="this.closest('picture').style.display='none'">…`. The `onerror` fallback to the brand-gradient swatch (see below) still applies to the `<img>`; hide the whole `<picture>`, not just the tag, so the gradient background shows through cleanly.

**Real-photo slots degrade gracefully.** Any `<img>` pointing at a real photo (e.g. `uploads/restaurante-*.jpg`, `uploads/barberia-hero.jpg`) must have an `onerror` fallback to the existing brand-gradient swatch — never a broken-image icon.

**Fonts load non-render-blocking, and only the weights actually used.** The Google Fonts `<link>` is loaded via the `rel="preload" as="style"` + `onload` swap trick (with a `<noscript>` fallback) so no text on the page ever waits on a font request — `font-display: swap` (already part of the Google Fonts response) handles the swap once it arrives. The requested weight list (`Sora:600;700;800` + `Inter:400`) is deliberately exactly what `css/styles.css` uses (per DESIGN.md Typography's One-Voice Rule: Sora carries headings/UI chrome at 700–800, Inter is body copy at regular weight only) — before requesting a new weight, check whether it's genuinely used; the previous, unaudited request pulled 9 weight files and 5 of them were dead weight.

**Logo assets are derived, not independent.** `assets/Logo.jpeg` is the single source original; `logo-icon.png` (tight crop, resized to its actual nav/footer display size, with a `logo-icon.webp` sibling) and the `favicon-*.png` sizes are generated from it. If the logo changes, regenerate all derivatives at a size close to their real on-page display (not the source's full resolution) and update the `width`/`height` attributes on their `<img>` tags in the template to match. Never force both `width` and `height` on a logo/icon `<img>` — set one and let the other be `auto`, or non-square ink visibly distorts.

**Design system source of truth is `DESIGN.md`**, not inference from the CSS. It documents exact palette hex values (all sampled from `assets/Logo.jpeg`), the "ribbon gradient is structural, never ambient decoration" rule, type scale (Sora display / Inter body, no second display face, no mono), component specs for every signature composition (Phone Mock, the six business-type tab directions, the UI Panel + Device Stack, tabs, FAQ accordion), and an extensive **Do's and Don'ts** list of things already tried and explicitly rejected (gradient-clip text, kickers/eyebrows, floating capability chips, overlapping device mockups, `overflow-x: auto` on the tab row, emoji-as-icons, fabricated client testimonials/case studies). Check this list before adding any new visual pattern — most "obvious" alternatives here were already tried and reverted for a documented reason. When you make a design decision worth remembering (a new named rule, a new signature component, a caught failure mode), update `DESIGN.md` to keep it as the durable record, matching its existing voice and structure.

**Design linting is automated.** `.claude/settings.local.json` wires an `impeccable` hook (`.claude/skills/impeccable/scripts/hook.mjs`) to run after every `Edit`/`Write` to a UI file and again on `Stop`, checking changes against the design system for drift (off-scale radii, unlisted colors/fonts, etc.). `.impeccable/config.json` holds `ignoreValues` — documented, reasoned exceptions (e.g. micro-scale radii under 24px elements, `#000` inside a CSS mask). If the hook flags something that's actually correct per an established `DESIGN.md` rule, prefer fixing the code to match the system; only add a new ignore entry with a real justification if the flagged value is a genuine, documented exception. Note the hook scans `index.html`/`en/index.html` (the generated output) and `templates/page.template.html` alike, since both are real HTML.

## SEO

`robots.txt` and `sitemap.xml` live at the repo root (served from the site root, listing both `/` and `/en/` with their `hreflang` alternates — keep the two in sync with the `<link rel="alternate" hreflang>` tags `scripts/build-pages.mjs` generates). Structured data (`Organization` + `WebSite` + `Service` JSON-LD, built in `buildJsonLd()` in `scripts/build-pages.mjs`) must only ever contain real, verifiable facts already present elsewhere in this repo (name, url, email, Instagram, `areaServed: "Costa Rica"`) — never invent a street address, hours, review/rating data, client count, or years-in-business; there is a `LocalBusiness` type available in Schema.org and it is deliberately not used here because there is no real, verifiable physical address to put in it (see PRODUCT.md Capabilities and Constraints on not fabricating social proof). `i18n/site.mjs`'s `url` field (`https://krevyon.com`) is the canonical production domain used to build every absolute URL in canonical/hreflang/JSON-LD/sitemap — update it there (and in `sitemap.xml`/`robots.txt`) if the real domain ever differs.

## Language

Spanish is the default, primary language; an English translation is available at `/en/` via the nav language switch (see Architecture above — real navigation between two static pages, not a client-side toggle). Within either language, never mix in loanwords from the other when a natural equivalent exists (Spanish copy must not say "Mobile", "Responsive", "Landing Page", etc. — see the durable rule on this in memory/CLAUDE.md history). Copy is professional, direct, no empty superlatives (see `PRODUCT.md` Capabilities and Constraints), and written so a business owner with no technical background understands it — explain the benefit of a technology before naming it, and only use technical terms (React, WebGL, API, etc.) in a section explicitly about technical capabilities, always paired with a plain-language explanation of what it lets the client do. Code, comments, and file structure are in English/standard conventions.
